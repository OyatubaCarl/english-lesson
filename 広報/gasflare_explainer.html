Teacher Tacos ／ 技術ノート

先生ひとりに、データベースひとつ。

管理用のスプレッドシートをコピーして、デプロイして、出てきたURLを配る。 それだけで、そのURLを踏んだ生徒の学習記録が、その先生のシートにだけ溜まっていく。 サーバも、データベースも、Google Cloud Console も要らない。

Plate 01 ／ 設計の起点

GASは、なぜ惜しいのか。

Google Apps Script には、学校で使う道具として他に代えがたい強みが3つある。

ひとつ、教員個人の権限のまま、生徒の情報を集められる。 情報システム部門に申請して、サーバを借りて、承認を待つ——そういう手続きが一切いらない。先生が自分のドライブでボタンを押すだけで成立する。

ふたつ、データが完全にその先生のものになる。 スプレッドシートは先生のドライブの中にある。誰かのサーバに預けるのではない。消すのも、渡すのも、持ち出すのも自由だ。

みっつ、Googleアカウントと成績が紐づくが、それは学校が発行したアカウントだ。 厳密に個人を特定しにいく仕組みではないし、私的な情報が混ざり込むわけでもない。 学校という文脈のなかで、ちょうど必要なぶんだけ本人が分かる。この距離感がいい。

——それでも、GASだけで全部を作ろうとすると、必ず壁に当たる。

壁1：配ったコードは、もう直せない

GASでアプリを作って配るということは、先生ごとにコードのコピーを配るということだ。 バグが見つかっても、仕様を変えたくなっても、こちらから直す手立てがない。 新しいものをまた配って、コピーし直してもらうのを待つしかない。

これは決定的だ。学習アプリは、使われはじめてからが本番で、直したい場所は毎週出てくる。 「直せない」を前提にすると、作れるのは、ほぼ完成していて、もう変わらない、単純なものだけになる。

壁2：リッチにすると、重くなる

GASでも画像は扱える。セルに Base64 で埋め込んでしまえばいい。 だが数が増えると途端に苦しくなるし、動作も鈍る。音声となればなおさらだ。

こちらが作りたいのは、イラストが出て、音声が鳴って、リズムに合わせて単語が飛んでくるアプリだ。 画像と音声の置き場所として、スプレッドシートは向いていない。

結論：変わるものと、変わらないものを引き離す

強みは 「先生の権限で、先生のものとして、記録が集まる」という一点にある。 弱みは 「更新できない」「重い」という二点にある。

ならば、強みの部分だけをGASに残し、残りを全部そこから追い出せばいい。

追い出した先が Cloudflare だ。この組み合わせそのものを GASflare と呼んでいる—— GAS ＋ Cloudflare。片方の話ではない。2つを組み合わせること自体に名前を付けた。 片方だけでは、どうしても足りないからだ。

この切り分けが、そのまま設計の制約になっている

GAS側のコードは、先生にコピーされた瞬間に凍る。だからGAS側は、可能なかぎり薄く、汎用的に作ってある。 受け取るのは「項目ID・見出し・セルに出す文字列・数値」という、アプリの中身を知らない形だけだ。

新しいゲームを足しても、問題形式を変えても、集計項目を増やしても、GAS側は書き換えなくていい。 変わり続けるものは、全部Cloudflare側に置いてある。

生徒の側から見れば、話はもっと単純だ。 学校のアカウントさえあれば、どの端末からでも、続きから学習できる。 教室のChromebookでも、家のタブレットでも、同じ場所から再開する。アカウントが本人を、URLが先生を指している。それだけでいい。

Plate 02 ／ 全体像

アプリは1つ。
データベースは、先生の数だけ。

ふつうに作ると、こうなる。アプリがひとつのサーバに繋がり、全員の記録がひとつのデータベースへ流れ込む。 誰が誰の担当かはアプリが知らないので、あとから「3組だけ」を切り出す仕組みを別に作ることになる。

GASflare は逆を行く。アプリは記録先を知らない。 記録先は、生徒がどのURLから入ってきたかで決まる。 先生が自分のシートから発行したURL、その一枚の紙が、そのままデータベースの入口になる。

先生がやることは、これだけ

  1. スプレッドシートをコピーするファイル → コピーを作成。これで自分専用のデータベースができる。
  2. デプロイする拡張機能 → Apps Script → デプロイ。実行＝自分／アクセス＝全員。新しいURLが発行される。
  3. URLを配るデプロイで出てきたURLを、そのまま。Classroom でも QR でも黒板でもいい。踏んだ生徒の記録がこのシートに溜まりはじめる。

複数のGoogleアカウントでログインしていて、別のアカウントで開いてしまったら、 「アカウントを選んで開き直す」ボタンが出る。そこから学校のアカウントを選び直せばいい。

前提にしているのは1人1プロファイルの環境だ。Chromebook は構造的にそうなるし、 PCでもプロファイルを分ければ同じになる。学校の正式な運用では、アカウントの取り違えは起きない。

Google Cloud Console のプロジェクトも、OAuth クライアントIDも、サーバの登録も出てこない。 技術の知識がない先生でも、5分で自分のデータベースを持てる——それがこの設計の目的だ。

Plate 03 ／ 入場

「学校のアカウントだけ」は、
どこにも書いていない。

生徒が先生のURLを開く。ブラウザは script.google.com へ GET を投げ、Googleのセッションクッキーが自動で付く。 ——ここが、この仕組み全体で唯一クッキーが効く場面だ。

ここが設計の背骨

Apps Script の Session.getActiveUser().getEmail() は、スクリプトの所有者と同じドメインの利用者にしか、メールを返さない。 他ドメインの人が開けば、空文字が返るだけだ。

つまり「学校のアカウントのみ」という制限は、設定ではなく Google の仕様そのもので成立している。 他校の先生がこのシートをコピーすれば、その瞬間から許可ドメインはその学校に切り替わる。誰も何も設定しない。

トークンの中身

メールは、ここから先へは一歩も出ない。外へ出るのは stu_9f2c1ab77e40 のような不透明IDだけだ。 メールとIDの対応表は、先生のシートの students にしか存在しない。

Plate 04 ／ 記録

クッキーの効かない場所で、
どうやって名乗るか。

ここからが本題だ。ゲームは pages.dev、GAS は script.google.com。別のオリジンである。 ブラウザはクロスオリジンの fetch にクッキーを付けない。付けようとしても、GAS は Access-Control-Allow-Credentials を返せないので、ブラウザが拒否する。

つまりPOSTの瞬間、GASは「誰が来たのか」をGoogleのセッションからは知りようがない。 だから身元は、さっき渡した署名トークンで名乗る。これがこの設計の核心だ。

実際に飛んでいるもの

POST https://script.google.com/macros/s/AAA.../exec
Content-Type: text/plain;charset=utf-8   ← プリフライトを避けるため
（Cookie は付かない）

{
  "action": "record",
  "tt": "<payload>.<signature>",
  "entries": [
    { "item":"b3", "label":"B3 Tom's Day",
      "cell":"具材 3/5",      // 先生のシートのセルに出る文字列
      "detail":"11010",       // 端末をまたいで復元するための原本
      "plays":3, "clears":0, "perfect":false,
      "stats":{ "words":8, "tacos":0, "exams":0 } }
  ]
}

送るのは前回から変わった項目だけだ。端末は「GASが ok を返した項目」を覚えていて、 それと同じものは送らない。45課やっていても、動いた1課しか飛ばない。

Plate 05 ／ 時間

いつシートに書かれるか。
そして、落ちたらどうなるか。

壊してはいけない一線

GASが落ちていても、ゲームは絶対に止まらない。 進捗の正本は、あくまで端末の localStorage にある。クラウドはその写しにすぎない。 通信は全部 catch して黙って捨てる。生徒から見た違いは、右上に「☁️ 記録中」のバッジが出るかどうかだけだ。

Plate 06 ／ 攻撃

URLを知られたら、
何ができてしまうのか。

このURLは生徒全員に配る。掲示板に貼られることも、外部に漏れることもある。 だから「URLを知っている人に何ができるか」を、正面から並べておく。

やろうとすること結果なぜ
他人になりすまして書き込む
（トークンの sid を書き換える）		 不可 署名が合わなくなる。鍵は先生のGASの中にしかない。
トークン無しで書き込む 不可 bad_token を返して、何も書かずに捨てる。
他人の進捗を読む 不可 読み出しにも署名トークンが要る。
別の先生のトークンで書き込む 不可 鍵が違うので署名が通らない。そもそも送り先が別を指している。
他ドメインの人が入場する 不可 メールが取れず、トークンが発行されない。
友人の端末を借りてログインし、
友人の進捗を自分のものにする		 不可 端末の進捗には持ち主を刻んである。持ち主が違えばアカウント側を正とし、端末の分は送らない。記録に残るのは、先生のURLから入って学習した分だけ。
生徒のトークンそのものを盗む なりすませる セッションクッキーを盗むのと同じ危険度。だからURLバーからは即座に消し、期限を120日に切っている。
devtools で localStorage を書き換える
（本人が、自分の記録に嘘の数字を書く）		 防げない 進捗の正本が端末にある以上、構造的に不可能。どんなクライアント主導の設計でも同じ。

下の2行を隠さないことが大事だと思っている。「絶対に安全」ではない。 署名が守るのは「他人になりすませないこと」と「他人の記録が勝手に混ざらないこと」まで。 本人が、自分のアカウントで、嘘の数字を送ることは防げない。

だから、この記録をそのまま成績にはしない。 誰が取り組んでいて、クラスのどこがつまずいているかを見るための道具として使う。 そこを偽装する動機は薄いし、声かけの精度はそれだけで十分に変わる。

メールはどこにあるか

生徒のメールアドレスは、先生のスプレッドシートの外へ一歩も出ない。 アプリ（Cloudflare側）が持つのは stu_9f2c1ab77e40 という不透明IDだけで、 それが誰なのかを知る手立てはアプリ側には存在しない。対応表は先生のシートの students にしかない。

先生が見る「進捗」シートには、照合済みのメールが並ぶ。 先生には見える。アプリには見えない。——それが正しい形だと考えている。

Plate 07 ／ 結び

成績処理の道具として。

学習アプリを配ったところで、誰がどこまでやったか分からなければ、授業では使えない。 かといって、学校の名前でサーバを立て、データベースを管理し、卒業のたびにアカウントを整理する—— そんなものを一教員が背負えるわけがない。

GASflare の答えは単純だ。データベースは、先生が自分のドライブに持てばいい。 スプレッドシートは先生がすでに持っている。デプロイのボタンも、Googleがすでに用意している。 足りなかったのは、「そのURLを踏んだ人だけを、そのシートに繋ぐ」という一本の線だけだった。

先生は、URLを配る。生徒は、それを踏む。それだけで、担任ごとの独立したデータベースが立ち上がる。 引き継ぎも、卒業も、異動も、シートをコピーするか捨てるかで済む。

使っているもの

Google Apps Script（無料）／ Google スプレッドシート（無料）／ Cloudflare Pages（無料枠）。 サーバ費用はゼロ。Google Cloud Console のプロジェクトも不要。
