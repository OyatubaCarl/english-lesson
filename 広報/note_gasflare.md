## 本文

### 学習アプリを配っただけでは、授業になりません

英単語アプリを作りました。使ってください。——そう言って配って、それで終われるなら苦労はありません。

授業で使うとなると、必ずこう聞かれます。**「で、誰がどこまでやったんですか」**

やった人とやっていない人が同じ扱いになるなら、生徒は次からやりません。宿題にも、評価にも、声かけにも使えない。学習アプリが「配って終わり」になってしまう一番の理由が、ここだと思っています。

だから、学習記録が要ります。問題は、**それをどこに置くか**です。

### GAS（Google Apps Script）は、学校にとって奇跡的に都合がいい

先に結論を言うと、私は Google Apps Script が好きです。学校で使う道具として、**他に代えがたい強みが3つ**あります。

**ひとつ、教員個人の権限のまま、生徒の情報を集められる。**

情報システム部門に申請して、サーバを借りて、承認を待つ——そういう手続きが一切いりません。先生が自分のドライブでボタンを押すだけで成立します。これは、現場の人間にしか実感しにくい価値かもしれません。「やりたい」と思ってから「動いている」までの距離が、圧倒的に短い。

**ふたつ、データが完全にその先生のものになる。**

スプレッドシートは先生のドライブの中にあります。誰かのサーバに預けるのではありません。消すのも、渡すのも、持ち出すのも自由です。学校でデータを扱うとき、この「自分の手元にある」という感覚は、想像以上に大きい。

**みっつ、Googleアカウントと成績が紐づくが、それは学校が発行したアカウントである。**

厳密に個人を特定しにいく仕組みではありませんし、私的な情報が混ざり込むわけでもありません。学校という文脈のなかで、ちょうど必要なぶんだけ本人が分かる。**この距離感がちょうどいい。**

### それでも、GASだけで全部を作ると壁に当たる

ところが、GASでアプリそのものまで作ろうとすると、必ず二つの壁に当たります。

#### 壁1：配ったコードは、もう直せない

GASでアプリを作って配るということは、**先生ごとにコードのコピーを配る**ということです。

バグが見つかっても。仕様を変えたくなっても。こちらから直す手立てがありません。**新しいものをまた公開して、コピーし直してもらうのを待つしかない。**

これは決定的でした。学習アプリは、使われはじめてからが本番です。「ここの説明が伝わっていない」「この問題が難しすぎる」——直したい場所は毎週出てきます。

**「直せない」を前提にすると、作れるのは、ほぼ完成していて、もう変わらない、単純なものだけ**になります。

#### 壁2：リッチにすると、重くなる

GASでも画像は扱えます。セルに Base64 で埋め込んでしまえばいい。実際にやってみました。

でも数が増えると途端に苦しくなりますし、動作も鈍ります。音声となればなおさらです。

私が作りたかったのは、イラストが出て、音声が鳴って、リズムに合わせて英単語が飛んでくるアプリでした。**画像と音声の置き場所として、スプレッドシートは向いていません。**

### 気づいたこと：強みと弱みが、きれいに分かれている

並べてみて、はっとしました。

- GASの**強み**は、「**先生の権限で、先生のものとして、記録が集まる**」という一点にある
- GASの**弱み**は、「**更新できない**」「**重い**」という二点にある

そして、この二つは**混ざっていない**。強みは記録の話で、弱みはアプリの話です。

**ならば、強みの部分だけをGASに残して、残りを全部そこから追い出せばいい。**

### 答え：アプリはCloudflare、データベースはスプレッドシート

こうしました。

| | 置き場所 | 性質 |
|---|---|---|
| **アプリ本体**（UI・出題・画像・音声） | Cloudflare Pages | よく変わる |
| **本人確認と記録** | 先生のGAS ＋ スプレッドシート | ほとんど変わらない |

すると、こうなります。

- **直したいときは、Cloudflare側を1回直すだけ。** 全員に届きます。先生は何もしなくていい
- **画像も音声も好きなだけ載せられる。** ホスティングは、そういうもののためにあります
- **データは今までどおり、先生のスプレッドシートのもの。** そこは1ミリも譲っていません

そして生徒の側から見ると、話はもっと単純になります。

**学校のアカウントさえあれば、どの端末からでも、続きから学習できる。** 教室のChromebookでも、家のタブレットでも、同じ場所から再開する。アカウントが本人を指し、URLが先生を指している。それだけでいい。

この組み合わせを、私は **GASflare** と呼んでいます。**GAS ＋ Cloudflare** です。

どちらか一方の話ではありません。**GASとCloudflareを組み合わせること自体**に名前を付けました。片方だけでは、どうしても足りないからです。

### 先生の手順は3ステップ

1. **スプレッドシートをコピーする** — ファイル → コピーを作成
2. **デプロイする** — 拡張機能 → Apps Script → デプロイ（実行＝自分／アクセス＝全員）
3. **URLを配る** — デプロイで出てきたURLを、そのまま。Classroom でも QR でも黒板でもいい

複数のGoogleアカウントでログインしていて、別のアカウントで開いてしまったら、「アカウントを選んで開き直す」ボタンが出ます。そこから学校のアカウントを選び直せます。

前提にしているのは**1人1プロファイル**の環境です。Chromebookは構造的にそうなりますし、PCもプロファイルを分ければ同じです。学校の正式な運用では、アカウントの取り違えは起きません。

生徒がそのURLを学校のGoogleアカウントで開くと、そのままアプリが始まります。**そのURLを踏んだ生徒の記録だけが、その先生のシートに溜まっていきます。**

サーバは要りません。データベースも要りません（スプレッドシートがデータベースです）。Google Cloud Console も出てきません。費用はゼロです。

シートを開くと「進捗」ができていて、メニューから **「クラスの進捗を見る」** を選ぶとダッシュボードが開きます。

- **生徒ごと** — 到達率・学習済み単語数・最終学習日
- **項目ごと** — 達成した人が少ない順に並ぶ。**ここがクラスのつまずき**
- **一覧表** — 生徒 × 項目のマス目

### 「学校のアカウントだけ」は、どこにも書いていない

技術的にいちばん面白かったところです。

生徒が先生のURLを開くと、Apps Script は `Session.getActiveUser().getEmail()` で本人を確認します。この API には、こういう性質があります。

> **スクリプトの所有者と同じドメインの利用者にしか、メールを返さない。**

他ドメインの人が開けば、空文字が返るだけ。つまり **「学校のアカウントのみ」という制限は、設定ではなく Google の仕様そのもので成立している**わけです。

許可ドメインを書く設定ファイルは、どこにもありません。他校の先生がこのシートをコピーすれば、その瞬間から許可ドメインはその学校に切り替わります。誰も何も設定しない。

### なりすましは、署名で止める

生徒がURLを踏むと、Apps Script は**署名付きのトークン**を発行してアプリへ渡します。中身はこれだけです。

- **誰か** — メールではなく、`stu_9f2c1ab77e40` のような不透明なID
- **どこへ送り返すか** — その先生の Apps Script のURL
- **期限**

これを **HMAC-SHA256** で署名します。鍵は、その Apps Script が初回に自分で作った乱数で、**アプリにも通信路にも一切出てきません**。

だから、IDを書き換えて他人になりすまそうとしても署名が合わずに捨てられますし、「送り先だけ別の先生のGASに差し替える」こともできません（送り先も署名の中にあるので）。

### メールは、シートの外へ出ない

生徒のメールアドレスは、**先生のスプレッドシートから一歩も出ません。**

アプリ側（Cloudflareで配信している静的ファイル）が持っているのは `stu_9f2c1ab77e40` という不透明IDだけで、それが誰なのかを知る手立てはアプリ側に存在しません。メールとIDの対応表は、先生のシートの中にしかない。

先生が見る「進捗」シートには、照合済みのメールが並びます。**先生には見える。アプリには見えない。** これが正しい形だと思っています。

### 記録に残るのは、先生のURLから入った分だけ

もうひとつ、大事な原則があります。**端末に元からあった進捗が、あとからアカウントへ合流することはありません。**

localStorage は Googleアカウントに紐づかないので、「端末に記録がある」ことは「その人がやった」ことを意味しません。友人の端末かもしれない。だから進捗には**持ち主**を刻んでおき、違う人がログインしたらアカウント側の記録を正とします。**友人の端末を借りてログインしても、友人の成果が自分のものになることはない。**

### 「絶対に安全」ではない、とは書いておきます

URLは生徒全員に配ります。掲示板に貼られることも、外に漏れることもあるでしょう。だから正直に書いておきます。

**トークンそのものを盗まれれば、なりすませます。** セッションクッキーを盗まれるのと同じ性質の話で、署名で防げる種類のものではありません。だからURLバーからは即座に消し、有効期限を切っています。

そして、**本人が devtools で端末の記録を書き換えることは、構造的に防げません。** 進捗の正本が端末にある以上、どんなクライアント主導の設計でも同じです。

守れるのは「他人になりすませないこと」と「他人の記録が勝手に混ざらないこと」まで。だから私は、**この記録をそのまま成績にはしません**。誰が取り組んでいて、クラスのどこがつまずいているかを見るための道具として使う。そこを偽装する動機は薄いし、声かけの精度はそれだけで十分に変わります。

### 引き継ぎも、卒業も、シート1枚

この形にして良かったと思うのは、**運用が全部スプレッドシートの操作に落ちる**ことです。

- 学年が変わる → 新しくコピーして、新しいURLを配る
- 引き継ぐ → シートを共有する
- 捨てる → シートを削除する
- 他の先生に配る → シートを配る（コピーされた瞬間、前のデータは自動で消えます）

サーバの管理も、アカウントの発行も、データの移行も出てきません。**先生がすでに知っている道具の上で、全部が完結する。**

## 補足（記事には載せないメモ）

- 「なぜ Content-Type: text/plain なのか」「なぜアクセス＝全員でデプロイするのか」は note では深追いしない。誤解を招きやすいので、HTML解説ページに譲る
- GAS側を薄く汎用的に作ってあるのは、壁1（コピーされたコードは直せない）の直接の帰結。新しいゲームを足しても、集計項目を増やしても、GAS側は書き換えなくていい設計になっている
- 「満貫」は使わない（恒久フィードバック）
